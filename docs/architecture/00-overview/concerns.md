# 관심사 (Concerns)

**관심사**는 이해관계자가 시스템에 대해 궁금해하거나 중요하게 여기는 사항이다.
각 관심사는 하나 이상의 Viewpoint를 통해 대응된다.

| ID | 관심사 | 관련 이해관계자 | 대응 View |
|----|--------|-----------------|-----------|
| C1 | 도메인 규칙이 명확하고 코드와 일치하는가 | 개발자, 크루 스태프 | 01-domain |
| C2 | 주문 상태/진행률이 정확히 추적되는가 | 고객, 관리자 | 01-domain, 03-process |
| C3 | 가격(수량 티어·크루 할인)이 올바르게 계산되는가 | 고객, 크루 스태프 | 01-domain(business-rule) |
| C4 | 데이터 모델이 무결성을 보장하는가 (FK/제약/RLS) | 개발자, 관리자 | 02-data |
| C5 | 주문/취합/결제 흐름이 어떻게 이어지는가 | 전체 | 03-process |
| C6 | 외부 시스템(SSO/결제/알림) 계약이 안전한가 | IdP, Groble, 개발자 | 03-process, 04-interface, 06-quality |
| C7 | API/서버액션 인터페이스가 무엇을 노출하는가 | 개발자, 관리자 | 04-interface |
| C8 | 컴포넌트/레이어 구조와 배포 형태 | 개발자 | 05-architecture |
| C9 | 성능 (렌더링·캐싱·이미지 최적화) | 고객, 개발자 | 06-quality |
| C10 | 보안 (인증 격리·토큰·웹훅 서명·권한) | 관리자, 개발자, IdP | 06-quality |
| C11 | 유지보수성 (1인 개발, 변경 용이성) | 개발자 | 05-architecture, 06-quality |
| C12 | 관측성 (분석·알림·로그) | 개발자, 운영 | 06-quality |

## 핵심 아키텍처 결정과 관심사 연결

- **DDD 레이어링**(domain→application→infrastructure): C1, C11 — 규칙을 도메인에 응집, 인프라 교체 여지.
- **멀티테넌트**(기본 테넌트 `런하우스`): C4, C10 — 테넌트별 데이터/권한 격리.
- **커스텀 인증 3종 분리**(고객/크루SSO/관리자): C10 — 권한 경계 명확화.
- **취합=size_collection 재사용**(크루 스토어 상품도 collection): C1, C5 — 단일 파이프라인.
- **외부 결제(Groble 링크+웹훅)**: C6, C10 — 자체 PG 미보유, 서명/멱등성으로 정합성 확보.
